# 后台服务软件的申报说明书与程序化制图

本规则适用于 API、后台服务、模型网关、算法服务、SDK 等**不以图形界面为主要交互方式**的软件。软件著作权材料以真实程序与适用文档为依据，不强制编造前端页面。

## 先说明产品用途

在说明书开头明确：服务哪些业务系统、提供什么共同能力、如何调用以及为什么采用独立后台服务。避免仅按使用的技术库罗列功能；不能凭空推导行业专有算法、业务成效或技术原创性。

推荐顺序：

1. 软件用途和服务对象
2. 总体结构以及外部调用关系
3. API 接口、请求与响应结构
4. 主要业务能力及其处理流程
5. 关键模块、函数、算法和数据字典
6. 安装运行、配置依赖及异常处理

可继续采用用户提供的代理模板章节和字段，不另行创造模板要求。

## 技术图件

- **结构由软件源码、接口与实际架构决定。** 优先通过 Graphviz DOT、Mermaid、PlantUML、draw.io 或 Python 程序化生成，禁止以文生图模型生成虚构的技术架构图和操作截图。
- 每张图保存：可编辑源文件、SVG 或高清 PNG、图题、图注、相关代码路径或接口证据。
- 使用稳定的模块名称；外部模型服务、检索服务应与平台自有模块分开，箭头方向与实际调用一致。
- 图中文字应能在 WPS、Word 的 PDF 导出中清晰阅读，避免模糊、裁切、中文字形缺失。图名放在图下方，图下注明与软件处理逻辑相关的事实。
- 公式使用排版工具或可编辑的公式对象，检查数学变量、分式、上下标和导出结果，避免直接用图片代替本可编辑的公式而无源记录。

通用 Graphviz 制图命令：

```bash
python skills/copyright-forge/scripts/render_diagrams.py \
  --dot docs/architecture.dot \
  --output-dir output/figures \
  --formats svg,png,pdf \
  --dpi 200
```

工具同时生成带源文件与导出文件 SHA256 的 JSON 清单；需要 Graphviz `dot`。缺少 `dot` 时应明确说明未执行渲染，不应宣称图件已经检查通过。

## 源程序与文件追溯

- 建立固定的源码快照和稳定的源文件清单；交存程序应来自真实版本，不通过补写虚构注释、修改函数或重排伪装历史源程序。
- 正式交存页保留真实代码与必要页眉页码；另外建立**页码、相对文件路径、原始行号范围**的核对表。跨文件的页面应有多条对应记录。
- 对多文件程序采用可复现、可解释的确定性编排规则。不能随意调整先后顺序来规避连续交存要求；涉及商业秘密时核查是否可采用适用的例外交存方式。
- 申请表中的源程序量来自选定软件源码范围的统计，不等于交存 60 页的代码行数；代码来源变化时重新统计。
- 技术说明书、申请表与交存源码需保持软件名称、版本、模块和主要功能一致。仅有设计稿或候选算法补丁，不等于已经成为软件正式版本。

## 核查目标

交付前检查文件完整性、源代码来源、图像清晰度、公式显示、文字自然性以及需要申请人真实提供的权属事实。生产环境、真实业务数据或算法性能基准不是统一的软著文档生成条件。
